## 用户确认的待优化问题（P1，尚未修复）

**当前交互不够丝滑，haochen 的刘海入口与 Mac 原生物理刘海看起来断开。** 这不是用户已接受的完成态，不应仅标成可选美化；下一轮须提供实机前后录屏，并由用户本人验收。

### 建议改造顺序

1. **先定位割裂原因。** 在有刘海的真机记录显示器 ID、缩放、菜单栏自动隐藏、全屏和 Space 情况，对齐物理刘海边界、AppKit/Qt 坐标、像素取整、填充颜色、圆角、描边和阴影。现有 `notch.py` / `native_window.py` 已使用 safe area 和辅助顶部区域，不能把“补上 safe area”当作未经验证的答案；先确认究竟是位置、色差、遮罩还是窗口交接造成割裂。
2. **做成视觉连续的收展。** 有刘海机型应像从硬件刘海下缘延伸，而不是下面再挂一个独立胶囊；避免可见缝隙、双轮廓和突然换窗口。总览、动态详情、日报保持同一套展开/返回语言。无刘海外接屏允许使用浮动胶囊，不伪造硬件刘海；不覆盖菜单栏操作区、不全屏铺透明点击层。
3. **统一动画状态管理。** 使用一致的起点、锚点、宽高/圆角/裁切与内容出现节奏；连点、反向收起、Esc、⌘M 可以从当前进度自然接续，不重置跳帧、重复弹窗或丢失滚动/草稿。先测原生窗口与 WebView 的布局、重绘和主线程开销，避免只改 duration 或堆叠弹性效果。
4. **信息与窗口行为一起验收。** 刘海、桌宠、总览共用真实状态与未读数；提醒不抢焦点。打开来源仍让出前台，悬停不制造重复提醒。尊重 Reduce Motion，提供少位移/无弹跳降级；保留现有配色方向及右下角全局 haochen，不因本报告为深色就更改产品主题。

### 报告中优先观看的片段

- boring.notch、DynamicNotchKit、DynamicLake：刘海连接形态、容器形变、无刘海退化形态。
- Loop Stash、Sonner、Vaul：来自同一方向的收回、可中断动作、事件插入与让位节奏。
- CodeIsland：把 Agent 状态压缩为小而明确的提示；不照搬其形象或把未知状态伪装为工作中。
- 玻璃/hero/spring 示例：只作为材质和运动工艺参考；是否引入 SwiftUI/新库，须先验证与当前 AppKit + Qt + WK 架构、最低系统版本和分发约束的兼容性，不预设全面重写。

以上是基于用户报告整理的参考方向，不是本次已验证的第三方产品/API/许可结论。

### 交付验收

- 支持的有刘海机型在浅色/深色壁纸、不同缩放下看不到两块独立入口的缝隙或色块；无刘海外接屏入口位置正确。
- 连续收展至少 20 次，并在动画中反向操作；无闪白、残影、突然跳变、重复窗口或状态丢失。
- 测试 ⌘M、Esc、来源跳转、菜单栏自动隐藏、全屏/Space 切换、外接屏热插拔与 Reduce Motion；输入焦点和用户其他应用不受错误遮挡。
- 在目标设备录制前后对比并测量帧时间/卡顿，而不是用“已设置 60 fps / spring”代替观测。具体性能阈值结合目标机刷新率与基线先对齐，不牺牲信息量或抓取质量。
- 用户亲自验收；本轮没有重新启用独立“高审美验收 agent”。
