## 阶段二：定向复验

## 最终裁决：NOT PASS

短结果计时、详情竞态、错误设置状态和整体人物/气泡审美基本达到交付水准，但仍存在三个重要的可信度问题：

1. 点击“不读”后，顶层气泡过快消失；约 1.0 秒和 1.7 秒均只剩人物，用户无法确认“没有读屏”，也看不到自然衔接的最终回答。
2. 同意读屏后实际因权限不足而失败，但详情工具卡却显示 `read_screen ✓ 完成`，与可见结论直接矛盾。
3. 拒绝读屏的隐藏详情中续答了此前已停止的“专注力”旧问题，存在上下文串线。

重要问题未清零，因此裁决为 **NOT PASS**。

## 阻断交付的重要问题

### I-01：拒绝读屏后顶层没有可确认的拒绝状态或最终回答

- 严重度：重要
- 置信度：高
- 复现次数：2 次独立拒绝路径
- 步骤：在有效环境请求读取当前屏幕；看到“点『读吧』允许；点『不读』拒绝”后点击“不读”；连续观察顶层状态。
- 实际：
  - 第一轮约 1.062 秒、1.165 秒、1.798 秒时均只剩人物。
  - 第二轮约 1.082 秒、1.200 秒、1.811 秒时均只剩人物。
  - 没有可见“已拒绝”“没有读取屏幕”或最终回答，也没有“查看详情”入口。
  - 只有在后来完成另一轮请求并进入完整会话后，才能看到拒绝记录。
- 0.2 秒限制：CUA 按钮点击调用本身约耗时 1.08 秒，无法可靠取得点击后 0.2 秒画面；另一次键盘尝试没有真正触发“不读”，不作为证据。
- 预期：点击后至少在 1.0 秒和 1.7 秒明确显示“已拒绝，未读取屏幕”，再自然过渡到最终回答。
- 用户影响：用户无法确认隐私选择是否生效；当前请求看起来像凭空消失。
- 证据：两轮 AX 树在拒绝后都只剩 `haochen，点击开始对话`；截图 `stage2-05-refused-top-level-at-1s-pet-only.png`。

### I-02：读屏实际失败，但详情工具卡显示成功

- 严重度：重要
- 置信度：高
- 复现次数：1 次
- 步骤：请求读屏并点击“读吧”；看到运行态；系统提示未检测到授权时选择“暂不”；查看结果和详情工具卡。
- 实际：运行态显示“正在读取屏幕 / 已允许，正在读取当前屏幕”；系统随后提示“仍未检测到授权”；顶层结论说“读不了屏：haochen 还没拿到『辅助功能』权限”，但详情工具卡仍显示 `read_screen ✓ 完成`。
- 预期：工具卡显示“失败”“未执行”或“权限不足”，不能显示完成。
- 用户影响：同一界面同时声称“完成”和“读不了”，用户无法判断屏幕是否实际被读取。
- 证据：`stage2-01-tool-cards-refused-and-permission-error.png`；AX 树同时记录完成工具卡和权限失败结论。

### I-03：拒绝读屏后续答了此前已停止的旧问题

- 严重度：重要
- 置信度：中高
- 复现次数：1 次
- 步骤：请求“详细列出十条提高专注力的方法”并立即停止；新提问要求读取当前屏幕；点击“不读”；稍后查看完整会话。
- 实际：工具卡正确显示 `read_screen 未执行 · 已拒绝/超时`，但其后结论变成“没读屏——你拒绝了读屏请求，所以下面只讲专注力”，并继续生成十条专注力建议。
- 预期：当前屏幕请求被拒绝后，只说明未读取、无法回答当前屏幕内容，并给出继续方式；不恢复上一条已停止任务。
- 用户影响：当前意图与上一任务串线，用户会怀疑停止没有生效或会话状态不可预测。
- 证据：`stage2-02-refused-tool-card-and-wrong-context.png`。

## PASS 项

### 短结果生命周期

三次“首答 → 第二答”精确复验均未复现第二次结果立即消失：

| 轮次 | 场景 | 发送至出现 | 第二结果可见时长 |
|---|---|---:|---:|
| 1 | 不打开详情，A→B | 1.447 秒 | 11.539 秒 |
| 2 | C 结果打开详情→Esc→立即问 D | 1.678 秒 | 12.607 秒 |
| 3 | 不打开详情，E→F | 1.442 秒 | 11.874 秒 |

额外一次结果约 1.677 秒出现；出现后约 2 秒和 10 秒仍可见，约 13 秒已自动退场。短结果生命周期 **PASS**。

### 详情竞态

- 打开详情约 744ms，Esc 关闭约 639ms。
- 关闭后立即再次提问成功，新结果保持约 12.607 秒，没有被旧计时器清除。

“查看详情 → Esc 立即关闭 → 立刻再问” **PASS**。

### 拒绝工具卡语义

完整会话中的拒绝读屏工具卡显示 `read_screen 未执行 · 已拒绝/超时`，没有把用户拒绝本身说成成功。工具卡顶层语义 **PASS**，但桌面反馈和上下文仍因 I-01、I-03 不通过。

### 错误环境最终态与设置

- 首次请求约 1.083 秒后显示单一错误“API Key 无效或格式不正确”，只有“检查设置 / 重试”。
- 三次用户触发的重试后，AX 树中错误正文计数始终为 1，没有堆叠恢复气泡。
- 设置明确显示 `deepseek 当前凭据验证失败` 和“API Key 无效或格式不正确，请重新输入并验证”。
- 关闭设置后，原错误正文和“检查设置 / 重试”上下文完整恢复。

证据：`stage2-03-error-settings-explicit-failure.png`、`stage2-04-error-context-after-settings-close.png`。以上均 **PASS**。

### 自动恢复限制

无效 Key 被产品直接分类为终态错误，没有观察到可区分的自动恢复 1/2/3 顶层状态。三次可验证的是用户触发的“重试”，不是三段自动恢复。初始提交到最终错误只约 1.083 秒；若内部存在更短尝试，CUA 无法捕捉。本项列为未覆盖，不把不可见行为冒充已验证。

## 研发复核说明（验收封存后补充）

以下内容是研发侧在验收报告封存后的证据复核，不改写验收 Agent 当时看到和作出的判断：

- I-01 的关键 PNG 实际只截取了 `256×256` 的人物窗口，没有包含独立的气泡窗口；同一轮全新隔离目录的应用日志显示，拒绝后气泡先进入 `COMPOSING`，约 `1.59s` 后进入 `PRESENTING`，并继续保留约 `12s` 才自动退场。因此，“拒绝反馈完全没有显示”不能由该截图证明。研发仍确认了一个真实问题：用户点击“读吧”之前，系统权限引导已由工具开始事件提前触发，会抢焦点并遮盖确认流程。
- 阶段二后两项测试通过 `open -n -a` 启动；该方式没有可靠继承命令行内的隔离环境变量。I-02、I-03 的会话因此落入默认数据目录，而非报告声称的全新 `HAOCHEN_HOME`。I-02 的嵌套错误字段和 I-03 的中止上下文串线均已从实际会话记录独立复现，问题本身成立，但环境声明不成立。
- 对应修复为：只在用户明确同意读屏后触发系统权限引导；同时识别工具结果外层与内层的 `isError/details`；构造下一次模型上下文时，将已中止回答及其对应的用户请求一起排除。

第 7 轮复验必须直接启动 App 可执行文件并验证新会话只写入指定隔离目录；全屏取证必须同时包含人物和气泡窗口，不能再用单窗口截图推断顶层气泡是否存在。
