# haochen 0.5.0-beta.2 本地迭代记录

目标：解决 beta.1 实机反馈，交付能从刘海/桌宠唤起、状态真实、来源可跳转的本地候选。所有者自行验收，本轮不公开发布。

## 实施与验收顺序

1. 刘海作为轻量状态入口，桌宠保留对话/总览入口；两个入口共用单例与已读状态。
2. 展开总览为普通窗口；⌘M 收回刘海、Esc 逐层关闭，不丢草稿、层级与滚动位置。
3. Otty 真实 CLI 生命周期诊断、精确跳转与显式配置步骤；未知不等于空闲或任务完成。
4. Chrome 扩展 → 固定 ID 本机桥接 → 逐站授权 → 页面追踪 → 精确返回原标签。
5. 微信先验证公开可读边界：Dock 标记/应用跳转，不挖私人数据库，不把进程存在当消息已连接。
6. 单元/安全/真实 WK/旧桌宠回归 → legacy DMG → 移除旧安装 → 安装新包 → 实际操作链验证。

## 已核实的限制与设计

- macOS 物理刘海内没有可绘制屏幕；入口连接在其下缘，不覆盖菜单项。无刘海显示器使用顶部胶囊。
- 用户查看某一内容版本才回执已读；更新在途时旧回执不能清除新内容。已有普通事件建立安静基线，待确认状态立即可见。
- Otty 安装状态不能仅按默认配置目录推断；实际官方 CLI 上报优先。安装 Pi/OMP 集成必须先展示计划再确认，不覆盖已有文件、不重启用户 Agent。Codex/Claude 引导至 Otty 官方设置，不改写用户全局 hooks。
- Otty 1.4.1 的公开 CLI 暴露当前状态，不提供可回放的事件序列或 turn 计数；`watch` 仍然是轮询。本版总览收起后也约每 3 秒检查 Otty（原为 20 秒）。这能改善可见延迟，但不能保证捕获两次检查之间已完成的极短状态。若要求每轮完成必达，后续需经用户同意接入持久化 hook 事件收件箱，不能宣称仅缩短轮询就已解决。[官方 CLI](https://docs.otty.sh/reference/cli)
- Chrome 未连接时无法确定扩展是否已经安装，因此显示“待确认扩展连接”，而不是误报未安装。
- 本机微信已登录；实测聊天窗口 AX 仅暴露窗口外壳。Dock 的微信项可通过准确 App URL 定位，但本轮首次检查未返回 AXStatusLabel，不能据此声称零未读。
- 微信仅在公开 Dock 标记确实返回数字时显示相应数字；未暴露、超时或权限失效时标记为未知，保留的旧数字标注失效，不冒充当前值。尚需实际来信确认正向提醒链路。
- Apple 的 UNUserNotificationCenter 面向应用自身通知，不作为读取其他应用消息的全局接口。[Apple 文档](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter)
