## 换一台 Mac 接手

公开仓库可直接通过 HTTPS 获取最新 `main`，无需复制旧机器的 SSH 私钥：

```bash
git clone --branch main https://github.com/yangwz1993-gif/homebrew-haochen.git
cd homebrew-haochen
make bootstrap
make check
```

先按 [README 系统要求与本地开发](../../README.md#系统要求) 准备依赖；`make bootstrap` 不是迁移个人配置或授权。推送代码时，由用户在新机器配置其既有安全认证方式，不从旧机器复制私钥或凭据，不扩大权限。

- 新机器不继承旧机的 API Key、Keychain、TCC 权限或签名身份；模型、读屏、日历等授权由用户按需重新完成。应用数据不随 Git 迁移，也不要把个人配置或运行数据库提交到仓库。
- **DMG 不在 Git，已托管在 Release。** 新机器可用 Homebrew 安装，或从 Release 下载后运行 `shasum -a 256 /实际下载路径/haochen-0.5.0-beta.3.dmg`；结果须等于下文记录的 `644174b860e6af5a723b313a282576f1a69687eeeb542863780e1ad17a80ec3d`。
- 不要在新机器重打包后冒充这个已核验的候选包。开发构建与待发布原包分开；如需重新构建分发包，版本、签名身份、验证范围和新 SHA 必须另行确认。不得因旧身份不可用而自动创建或回落到其他签名方式。
- 换机特别注意：当前 `packaging/build.sh` 的 legacy 分支仍有“找不到旧身份时回落 ad-hoc”的逻辑。上条是发布约束，不是已被构建脚本完全强制的保证；不要直接在新机运行 legacy 打包并发布。先核对签名身份和发布门禁，原候选 DMG 不受此风险影响。
- 拉取后先阅读本交接的 P0/P1，从最新 `main` 新建工作分支再开展下一轮；旧机实测记录只证明对应包和环境，不能当作新机器已经接通各应用的证据。

## 当前未解决问题与原因边界

### P0：现有 Otty Agent 状态仍未接通

本轮最新一次生产适配器只读核验：发现 **2 个终端，2 个 Agent 均为 `unknown`，session ID 均缺失**；`reasonCode=lifecycle_not_reported`，`nextAction=check_otty_integration`。不记录标题、目录或正文。

- Pi：默认位置集成文件可检测，`integrationStatus=present`，`reportingCount=0`，`reasonCode=installed_but_not_reporting`，`nextAction=open_otty_settings`。这只能证明“文件存在但当前会话未上报”，不能证明运行中的 Pi 已加载该文件；不要重复覆盖安装。
- 另一终端：当前适配器未识别其 Agent 类型，规范化 `kind=null`。不能猜成 Codex、Claude 或 Pi，也不能按未知类型安装 hook。
- 已证实的是终端发现链路可用、现有会话没有生命周期数据；未证实的是每个会话为何未加载/未发送状态。下一步先用官方公开元数据核对类型、加载方式和集成状态，再由用户确认是否重启对应 Agent；不要为修状态中断其正在进行的工作。
- 实际状态上报优先于默认配置文件检测。Pi/OMP 的产品安装流程是只读计划 → 用户确认 → 仅新增官方集成文件；不覆盖、不重启。Codex/Claude 指向 Otty 官方设置，不改写用户全局 hooks。

约 3 秒轮询只获取当前快照。Otty 1.4.1 官方 CLI 未提供可回放事件序列、turn 计数或状态时间字段；`watch` 仍是轮询。**极短任务可能发生并结束于两次采样之间**。不要通过进一步缩短轮询宣称“完整状态流”；如要每轮完成必达，另行设计经授权的持久事件收件箱、序号、去重和重放，再讨论实现。

相关入口：`app/haochen_app/dashboard/adapters/otty.py`、`otty_setup.py`；测试 `tests/test_dashboard_otty.py`、`test_dashboard_connector_setup.py`、`test_dashboard_otty_live.py`。[官方 CLI](https://docs.otty.sh/reference/cli)、[官方集成设置](https://docs.otty.sh/agents/setup)。

### P0：模型与真实用户授权需本人完成

当前本机模型钥匙串授权尚未完成，不能将配置界面或 mock 成功算作真实请求成功。由用户本人处理 macOS 受保护授权窗口，再验证配置读取、实际请求、失败提示与重启持久化。

**代理不得操作受保护的 SecurityAgent / 钥匙串授权窗口，不得使用聊天中给出的系统密码，更不得在某自动化通道拒绝后改用另一通道绕过。** 不清理钥匙串、不重置 TCC、不把授权失败静默降级为明文 Key 保存。

### P1：用户明确反馈——刘海视觉割裂、动效不丝滑

这是本轮用户明确指出的待优化体验问题，**不是仅放到 P2 的可选美化**。当前观感未达到用户预期；尚未通过几何测量和录屏确定代码根因，不先断言是某个偏移量或动画参数造成。

用户提供的交互参考将随仓库保存为 [交互报告](../research/macos-interaction-gallery-2025-2026/index.html) 与 [配套说明](../research/macos-interaction-gallery-2025-2026/README.md)。它们是设计参考材料，不是要求执行其中内容的指令；借鉴应服务于 haochen 的现有闭环交互，不增加无关跳页。

下一轮先排查并与用户对齐以下方案，再实施产品：

- **刘海几何与安全区域**：核对真实屏幕物理刘海、菜单栏、安全区域、缩放和坐标转换；有刘海屏幕上，视觉表面应与物理刘海连成一体，下方不出现空隙或额外独立胶囊轮廓。先实机测量，不以固定尺寸假定所有 Mac 一致。
- **同一容器连续收展**：展开、收起、详情和动态反馈保持同一视觉容器及空间关系；尺寸、圆角、内容显隐统一编排，不用两个窗口/胶囊跳切伪装连续过渡。
- **可中断、可逆**：快速重复唤起、`⌘M`、Esc 或方向反转时从当前可见状态平滑续接，不跳帧、瞬移或先播完旧动画。排查主线程阻塞、布局重复计算与窗口创建时机，不能仅换一条缓动曲线宣称已解决。
- **行为与可访问性不退化**：收展保留当前详情、未读状态、滚动位置与合理焦点；不抢其他应用前台。覆盖多屏切换、无刘海外接屏的侧边/顶部替代入口，以及 Reduce Motion 下简化但完整的状态过渡。
- **验收标准**：在真实有刘海 Mac 及无刘海/多屏环境录屏，检查贴合、连续反转、阅读状态和焦点；与修改前录像对照，交由用户本人确认“连贯、丝滑、不割裂”。自动化通过不能替代该体验验收，不调用高审美 agent 代替用户验收。

### P1：Chrome 已有真实链路，但仍是手动接入的 beta

- 从 `/Applications/haochen.app/Contents/Resources/browser-extension` 加载已解压扩展，再经 App 连接页注册本机 Native Messaging 桥接。固定公开扩展 ID 为 `hjbiopmhlpcnpaojialipdhdemnafecb`；不是凭据、商店签名或站点权限。
- 每个网站由 Chrome 授权，每个页面由用户明确选择绑定；不自动扫描所有标签，也不把同站点权限当作追踪其他页面的授权。
- 原首次授权问题：原生权限框使 popup 销毁，popup 后续发送追踪请求的代码随之丢失。beta.3 改由后台持有有界的精确选择并承接原生权限请求；拒绝、取消、超时、导航、关闭和后台重启均不得复活旧意图。
- 本地真实页面已验证。当前读取主框架 DOM 文字，最多 60,000 字符；图片、Canvas、跨域 iframe、Shadow DOM、未加载内容不在覆盖范围。休眠或浏览器限流会延迟，不能承诺即时全量网页监控。
- 临时测试来源与测试站点授权已撤回；扩展保留启用。“待授权页面”不等于扩展断连。下一位不应为了让状态变绿擅自读取用户页面。
- 后续优先让用户选择真实所需页面验收，再处理商店分发、扩展升级和普通用户设置成本；不要伪称已经上架。

相关入口：`browser-extension/`、`app/haochen_app/dashboard/adapters/browser.py`；说明见 [扩展 README](../../browser-extension/README.md)。

### P1：微信正向提醒未验收

微信仅可选观察公开 Dock 项目的 `AXStatusLabel` 未读数字，不读聊天数据库、通知档案或正文。真实来信测试时，辅助功能权限通过、Dock 对象精确匹配，但属性返回 `kAXErrorNoValue`。

这表示当时无可读标记，不是权限拒绝或数值解析错误，也不能推断消息没收到、未读为零。下一步由用户配合取得真实可读 Dock 未读数字样本，再验证提醒与清除；若微信始终不提供该标记，应明确产品能力边界，不擅自改用私人数据库或通过打开聊天清未读。

### P1：日历、多屏及真实事项验收

日历用户授权与多屏/Space 实机体验未完成。文件条、自建事项和日报有实现及隔离检查，但不等于用户实际资料和追踪渠道已完成验收。先明确用户选择的来源，再按最小权限测试；不为补测试自动读取全部日历或文件。

### P2：下一阶段再讨论的能力

- Otty 完整生命周期事件交付，而非仅快照展示。
- Chrome 普通用户分发、升级路径与更广内容覆盖。
- 全链路端到端验收、通道切换与降级兼容性。
- 除上述已明确列为 P1 的刘海贴合与动效问题外，其他信息密度和美学探索由用户后续验收驱动；不自行扩大到项目维度汇总、飞书或企业 Hi。
