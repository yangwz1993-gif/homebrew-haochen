## 二、读屏失败 × 权限弹窗不关：根因与修复

### 根因（查明，非代码 bug）

1. **读屏执行体路径完全正常**：`haochen-reader --check`（可信环境）rc=0；`--json --no-scroll` 实读前台窗口成功（读到 cmux 12 段文本 / 详见 P4 真读屏「π - yangwz 终端窗口」）。
2. **真正的阻断是 .app 未被 macOS「辅助功能」实际授权**：本产品用 **ad-hoc 签名**。macOS 的 TCC 授权按「code 的 designated requirement」(DR) 认——**每次重建 `-`(ad-hoc) 签名，DR 都会变**。于是：
   - 你在系统设置里看到的「haochen 已开启」，那个勾选是**之前某次构建**的 DR 对应的授权；**当前构建的 DR 不同 → 系统不认 → 实际未授权**。
   - `AXIsProcessTrustedWithOptions`（permissions.py）按**调用进程的责任进程**判定，返回的就是真实的「当前构建是否被授权」——**结果为 False 是对的**（当前构建确实没被授权）。
   - 读屏失败 = 当前构建未授权（读屏执行体继承 .app 责任进程，同样未授权）。
   - 弹窗不关 = 点「我已授权」，但当前构建真没被授权 → 检测如实返回 False → 提示未授权（而非无限转圈）。**这不是检测 bug，是当前构建确实没被授权。**

### 已修复（健壮化，autonomous）

- `permissions.py`：引导卡片改为**非无限循环**——「我已授权」回查上限（3 次），超过则明确提示「可能未开启/需重启 App」，给出重启建议；按钮：去授权（触发系统弹窗 + 直达设置）/ 我已授权（回查）/ 暂不。
- `app_shell.py`：**读屏时刻再引导**——`read_screen` 工具调用时若未授权，自动再弹引导（防止启动时被「暂不」的用户错过）。
- `app/ext/index.ts`：读屏前先 `--check`；未授权 → 直接返回明确「需要辅助功能权限」错误（不再「先弹确认再失败」的困惑交互）；已授权 → 正常确认→读屏。
- `reader/haochen_reader.py`：新增 `--check` 模式（0=已授权 / 2=未授权）。
- 回归：M-C 5/5、M-E 17/17、L1 45/45、P4 25/25、真链路 16/16 全绿。

### 结论与需要的配合

**要让当前构建的读屏真正可用**，需完成**一次当前构建的授权**（这正是引导卡片的正常用途）：点「去授权」→ 系统弹窗点「打开系统设置」→ 在辅助功能列表打开当前 haochen → 回到卡片点「我已授权」→ 卡片关闭，读屏即可用（读屏执行体已实证可用）。

**要授权跨构建持久**（重新构建后不用再授权）：必须给 .app **稳定的签名身份**——
- 本地自签**受信任**证书（可使 DR 稳定、TCC 授权持久）；创建「受信任」证书需**一次管理员密码**（`security add-trusted-cert`）——这一步无法无头完成。
- 分发用 **Developer ID + 公证**（总纲 §五 既定）。

开发期临时方案：**每次重建后授权一次**（引导卡片已能正确闭环）。若产品希望我附上「自签受信任证书」的一键脚本（需用户输入一次管理员密码），我可以提供。
